# Tactus 版本路线图

当前开发发布版本：**0.02**。更新日期：2026 年 10 月 26 日。

Tactus 的目标是在 CKB 上构建高速 ZK based rollup：保留 EVM 开发体验，由 CKB 确定规范排序并承载数据，通过有效性证明结算，让独立参与者能够恢复状态、接手证明和处理资产退出。

推进顺序是：**协议完整 → 资产闭环 → 增量运行 → 独立接管 → 开放测试 → 持续高速。** 每个版本以可复现的验收结果完成，不按日期自动升级。以下版本是产品里程碑，与架构规范 v0.2.6、Cargo 包版本和证明程序身份分别管理；本路线图不修改现有部署或验证密钥。

## 版本总览

| 版本 | 定位 | 核心交付 | 完成标志 |
| --- | --- | --- | --- |
| 0.01 | 历史研究原型 | 排序、执行、证明与恢复的组件实验 | 已有局部证据，完整资产链路仍待完成 |
| 0.02 | 已发布开发里程碑 | 统一状态机、准入规则、停滞与退出设计 | 正常路径和主要故障路径都有明确规则 |
| 0.03 | 最小资产闭环 | 原生 CKB 存入、L2 使用、证明结算和取回 | 同一部署完成实际证明驱动的资产释放 |
| 0.04 | 持续增量运行 | 原生资产链路的增量证明与任务调度 | 历史增长不再要求每轮重放全部历史 |
| 0.05 | 独立运行与恢复 | 第三方接管、重组恢复、支持范围内的退出 | 原运营方离线后仍可恢复并完成结算与提现 |
| 0.06 | 开放测试网 | 钱包和开发工具、参与规则、监控与升级机制 | 外部参与者能独立部署应用和运行节点 |
| 0.07 | 高性能验证 | 代表性负载下的持续吞吐、延迟和成本报告 | 达到预先公开的性能门槛，积压保持稳定 |
| 1.0 | 生产候选 | 安全审查、可复现部署、运行与退出保障 | 所有适用的生产准入条件通过独立验收 |

0.02 已完成隔离开发实现与验收，并作为开发预发布版提供；0.03–0.07 仍是计划。版本完成不自动代表生产可用；各项安全与运行条件持续记录在 [生产准备状态](PRODUCTION_READINESS.md)。

## 0.01 当前研究原型

目前已经验证 EVM 执行与独立结果核对、CKB 数据发布、实际证明驱动的结算状态更新，以及部分恢复和重组处理。可选增量执行配置已经完成两个真实证明的连续结算。

固定原始负载的完整证明可比阶段耗时从 4,674.679 秒降到 830.397 秒；计入独立验证为 858.996 秒。结果包含代码优化与 CPU 线程配置变化。该负载为九个批次，前八个为空，最后一个有四个交易输入，不能据此推算真实业务 TPS。详见 [第三轮优化报告](SP1_OPTIMIZATION_ROUND3_REPORT.md)。

原生资产托管、发布与证明声明已有组件证据，但实际原生证明结算和资产释放尚未完成。增量证明的既有结果不赋予原生托管权限。当前所有 G1–G9 生产准入项仍为 OPEN。

## 0.02 协议架构闭合

完整研究稿见 [0.02 协议设计](V0_02_PROTOCOL_DESIGN.md)、[实施与验收计划](V0_02_IMPLEMENTATION_PLAN.md) 和 [研究审查记录](V0_02_RESEARCH_REVIEW.md)。0.02 已完成隔离开发实现与验收，并作为开发预发布版提供，详见 [验收记录](V0_02_ACCEPTANCE_AUDIT.md)和[发布说明](RELEASE_NOTES_0_02.md)。

本版先确定一套可以贯穿实现的协议。初始范围采用 CKB 排序与链上 DA、EVM 执行、SP1 证明，以及明确受支持的原生 CKB 资产路径。

- 统一交易、批次、存款和提现的生命周期，区分已接纳、已排序、已执行、已证明和可提现。明确 CKB 确认策略与重组影响。
- 确定生产候选排序和强制处理规则。保留 A1 作为正确性参考，继续验证 A3 不可变 sealed snapshots 的公平性与证明绑定；不以可变的实时依赖作为规范批次的稳定依据。
- 定义接纳前拒绝和接纳后确定性失败的边界，以及字节数、执行量、见证与证明资源上限。规范批次不能靠事后任意跳过来恢复结算。
- 定义未结算积压上限、过载处理、强制消息处理义务，以及停滞时可继续使用的恢复和退出路径。上限须有协议约束，不能只靠某个服务自觉限流。
- 定义支持资产的正常提现、无人出证明时的应急处理、升级权限和退出窗口。逐项列出证明者、数据保管者和 CKB 交易纳入的活性假设。
- 固定链身份、程序与验证密钥、状态承诺及升级绑定关系；列明费用承担方和接管者取得任务所需的数据。

**验收：**交付统一状态转换表、权限与信任假设表、资源限制表和故障矩阵。恶意批次、持续遗漏、队列饱和、prover 停机、数据缺失、重组和升级都能对应到明确的协议结果与后续验证用例。设计完成不等于抗审查或退出机制已经通过实测。

## 0.03 最小资产闭环

先以原生 CKB 为支持资产，在同一部署完成：

```text
CKB 存入 → L2 入账 → 转账或合约调用 → 提现扣款
        → 实际证明 → CKB 结算 → 释放 CKB 给用户
```

把现有托管、规范排序、发布、执行、证明和释放组件接成一条路径。证明同时约束状态变化、存款处理位置和提现结果，链上规则验证它们属于同一协议实例。完整重放可以作为本版的起点。

**验收：**多用户、连续至少两个结算区间完成真实资产释放；拒绝重复入账、重复提现、错链、错密钥和错误状态的证明；核对托管余额、L2 资产和在途存取款的守恒关系。验证重组后不会重复入账或释放。独立复现者能从部署说明重现整个过程。

实现入口见 [原生证明工作流](NATIVE_PROVING_WORKFLOW.md)。

## 0.04 持续增量运行

将经过认证的增量执行接入原生资产闭环。每轮从上一已认证状态开始，证明新增交易、存款和提现得到的新状态。保留完整重放作为核对与恢复基准，缓存和本地数据库只承担加速作用。

增加持久化任务队列、见证构建、重试、幂等提交和竞争提交处理。明确相邻证明区间的状态依赖；只有经过验证可安全并行的任务才并行，不能假设增加硬件就能线性扩容。证明程序变化使用明确的新身份和重新验证的部署配置。

**验收：**固定新增工作量、逐步增加历史长度，对比证明时间、见证准备时间、内存和磁盘开销；每轮不再要求完整历史重放。连续增量证明完成实际原生提现，进程中断和重复提交不会改变资产结果。全量重放与增量状态一致。

## 0.05 独立运行与恢复

实现完整节点接管流程：第三方从公开 CKB 数据与公开程序重建状态，自行构造见证、生成证明并提交结算，不依赖原运营方数据库或私钥。明确归档数据的保留、获取与校验责任。

统一排序、存款、执行状态、结算状态和提现的重组回退。实现 0.02 选定的支持资产退出规则，分别验证有人接手证明的正常退出，以及无人继续证明时的应急路径。旧状态根不会自动提供任意 EVM 合约资产的退出能力；无法保障的资产状态必须明确限制。

**验收：**关闭原运营方服务，由独立参与者在新环境恢复、生成新证明、结算并完成提现；通过计划和非计划重组、数据源故障、重启及恢复演练。应急退出所需交易可由用户独立构造；如果这一性质未实现，本版不能声称已经具备它。

## 0.06 开放测试网

让外部开发者能用普通钱包、Foundry、Hardhat 或 viem 部署和调用合约，RPC 清楚区分执行结果、排序确认与证明结算。发布固定 EVM 版本、兼容性范围和已知限制。

开放 builder、prover 和节点运行说明，明确费用、奖励或补贴来源、任务接手和故障责任。部署积压、结算延迟、资产对账和数据可用性监控。落实验证密钥与脚本升级规则，并演练升级通知期内的退出。

**验收：**外部参与者独立部署代表性应用、运行节点并完成存取款；在公开配置下进行持续运行和故障演练。该阶段使用测试资产，生产资金准入仍由独立条件决定。

## 0.07 高性能验证

把“高速”变成预先定义的可测目标。先根据应用需求、可用 CKB 带宽和硬件预算公布吞吐、延迟、成本与恢复时间门槛，再进行验收，不能用测试结果倒推通过标准。

| 指标 | 测量口径 |
| --- | --- |
| 持续有效吞吐 | 单位时间实际完成结算的有效交易，按交易类型和执行量分组 |
| 用户延迟 | 分别记录接纳、排序确认、证明结算和可提现的 p50、p95、p99 |
| 证明能力 | 包含见证准备、执行、证明、聚合和验证的端到端时间及资源 |
| 队列稳定性 | 持续负载下的积压、最长等待时间和过载后的恢复时间 |
| 数据与结算成本 | 每笔交易的 DA 字节、CKB 费用与容量占用、证明验证 cycles |
| 运行成本 | prover 硬件、节点与归档成本，列明利用率和补贴 |

负载至少覆盖转账、合约部署、DEX 交互、存储密集操作、验签密集操作和无效输入。固定软件版本、硬件、区块数、交易数及负载组成，公开原始数据；如比较 Godwoken，应使用可复现的对应配置和明确的安全、DA 与确认口径。

优化优先来自实测瓶颈：批次与数据编码、见证和状态访问、密码学加速、GPU、证明流水线；必要时比较不同 prover 或 EVM 专用证明方案。

**验收：**在预先公布的持续负载与运行时长下达到性能门槛，积压不持续增长，突发负载后能恢复，且成本处于预算内。单个证明耗时和浏览器显示的交易数均不能替代持续结算吞吐。

CKB 排序和确认节奏仍限制强确认延迟，链上 DA 带宽仍限制吞吐。预确认可以独立研究，但必须说明额外假设和失效处理，不能把预确认计为最终结算。

## 1.0 生产候选

在所有适用的 G1–G9 条件通过后，完成独立安全审查与问题修复复核、可复现构建与部署、证明系统参数和密钥来源审查，以及长期运行、恢复、退出和升级演练。明确上线资产范围、容量上限和事故响应流程。

1.0 不以超过 Godwoken 某一项指标作为放行条件。生产准入取决于 Tactus 自己公布的安全、功能和性能门槛，以及第三方能够复核的证据。

## 并行研究方向

Jolt Pro 与其他 prover、CKB 风格模块化授权及专用证明路径、原生 RISC-V 合约和 DEX 批量结算可做有边界的研究实验。它们只有在明确改善已测瓶颈或满足产品需求时，才进入主线路线图。

外部 DA 会改变 O1 的数据可用性假设，应作为单独配置或产品方向评估，不能作为解决 CKB 带宽限制的静默替换。

最近的工作落点是 **0.02 的协议设计与验收用例，以及随后 0.03 的真实原生资产闭环**。性能数据持续采集，架构与资产安全条件不会因某次加速结果而被跳过。

原生 RISC-V 的独立[实验设计](RISCV_EXPERIMENT_PLAN.md)与[框架](../experiments/riscv-contracts/README.md)已在 0.02 隔离验收后准备，尚未编译或运行。主线继续 0.03 资产闭环与 0.04 增量化；实验不会自动改变产品执行环境。
